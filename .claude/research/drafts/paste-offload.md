# 긴 붙여넣기를 파일로 빼는 입력 다듬기

사용자 (2026-11-17): "user input 에 훅을 걸어서 다듬어서 내는거. 예를 들어서 내가 긴 로그를 붙여넣었다 하면 이건 grep 이나 다른 접근법으로 보는게 맞을 수도 있잖아. tmp 에 임시 파일로 저장하고 보도록 하거나, 박스 렌더링 글자들이 하네스에서 그려진 테이블 같은걸 복사해서 넣는다 하면 지저분한데, 이걸 적당히 캐치해서 기본 markdown table 문법으로 만들어 준다던가" / "스테이징 서버에서 실제 테스트 하는 쪽에서는 프로덕션 로그 일부를 마스킹 해서 보거나 하는데 보통 입력 통로가 붙여넣기다 보니까 중간에 '──── (45 lines hidden) ────' 같은게 나타날 만큼 길어지기도 하거든. 그냥 생각 해봤던거로만 넣어두자"

## 되는 것
- command 훅(UserPromptSubmit)은 입력을 바꾸지 못한다: 맥락 덧붙이기와 막기만.
- mod 는 바꾼다: `on('prompt.submit', ($, e, next) => next({ ...e, text }))`. `e.text` 는 붙여넣기가 펼쳐진 뒤의 글이다. 출처: plugin-authoring `types/claude-code.d.ts` 의 `PromptSubmitInput`. qwreey-desk 가 이미 mod 라 거기에 붙일 수 있다.
- 엔진은 mod 가 덧붙인 `context` 항목만 100,000자 넘으면 머리와 경로로 줄인다. 사용자 입력 글은 대상이 아니다.

## 잰 것 (2026-11-17, 이 기계의 모든 프로젝트 transcript, `<pasted_content>` 기준)
- 사용자 메시지 2,607, 붙여넣기 35, 합계 40,320자, 5k자 넘는 것 0, 최대 3,910자(quad). 상자 문자 붙여넣기 2.
- 한계: `<pasted_content>` 로 감싸지 않은 붙여넣기와 30일보다 오래된 transcript 는 빠진다. 회사 스테이징 쪽 사용은 이 기계에 없다.

## 만든다면
- 원문을 바꾸지 않는 쪽만: 긴 붙여넣기(예: 8k자 넘음)는 원문을 파일로 저장하고 입력에는 앞뒤 몇 줄과 경로를 남겨 grep 으로 보게 한다. 상자 표는 붙여넣기 안에서만 markdown 표로. 글머리 기호 바꾸기는 이득이 없다.
- 사용자 원문을 쓰는 곳이 바뀐 글을 원문으로 알게 되는 문제: 세션 기록, compact 뒤 원문 복원 앵커, desk 답, advisor `user-asks.py`. 원문 파일 경로를 남기고 이들이 그 경로를 따르게 하거나, 바꾼 글에 표시를 단다.
- 마스킹 로그는 민감할 수 있다: 저장 파일은 저장소 밖 임시 폴더, 세션 끝에 지운다.
- 측정: 회사 동료 환경에서 붙여넣기 길이 분포를 같은 스크립트로 잰 뒤 결정.
