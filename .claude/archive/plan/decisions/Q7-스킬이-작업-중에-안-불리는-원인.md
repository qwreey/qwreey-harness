# Q7. 스킬이 작업 중에 안 불리는 원인 조사: 이 방식으로 할까?

## 맥락

**처음 질문(사용자 원문, audit 56 뒤):** "스킬이 읽히지 않는건 이유가 약간 다른것 같음. 룰도 요청 내용처럼 실릴거고, '자세한건 보라' 는데 그 자세한건 봐야할 동기가 없는거 아닐까 … rules 에서 skill 이 언급되는 경우 어떤 동작을 띄는지는 좀만 더 연구를 해봐야하나"

**어디서 어긋났나:** audit 57 은 이 질문을 쟀다(포인터 꼴별). 그 뒤 외부 조사에서 사용자 프롬프트 정규식 라우터가 나왔고, 그걸 시험한 것이 audit 60 이다. 그건 "사용자가 무엇을 말했나" 만 보므로 에이전트가 작업 중에 스스로 마주치는 상황(함수를 쓰다 주석을 달 때, 이전 프롬프트의 "끝나면 테스트" 같은 맥락)은 보지 못한다. D1 답대로 버린다.

**알고 있는 것**
- 실제 기록 36~73개에서 comments 스킬 로드 0, code-reuse 2~3, agent-docs 1~2 (audit 56).
- 스킬은 description 이 그 순간의 과제 표현과 맞을 때만 로드됐다(audit 57: 기록해 줘 3/3, 함수 쓰다 주석 0/3).
- opus 는 "Before you <행동>, load" 에만 반응, sonnet 은 어떤 꼴에도 0.

**제안하는 조사(원인 찾기)**
1. 실제 세션 기록에서 "스킬이 불렸어야 했는데 안 불린" 순간을 모은다(스킬 영역의 파일을 쓰거나, 스킬이 다루는 결정을 내린 순간). 그때 모델이 본 것(스킬 목록 description, 주입된 rule, 직전 행동)을 함께 뽑는다.
2. 그 순간들을 유형으로 나눈다: 과제 표현과 description 이 어긋남 / 모델이 이미 안다고 판단 / rule 이 이미 충분 / 목록에서 밀려남 등. thinking 이 보이는 기록이면 건너뛴 이유도 본다.
3. 유형마다 맞는 고침을 찾는다: description 을 상황(행동) 말로, 꼭 필요한 사실은 행동 시점 훅이 직접(comment_language 처럼), 스킬을 rule 로 합치기 등. 그다음에만 실측.

비용: 1~2 는 기록 읽기라 sonnet 서브에이전트 한두 개, 약 USD 2~4. 실측은 그 뒤 따로 정한다.

## 선택지

- a) 이 방식으로 조사
  실제 놓친 순간부터 보고 원인별로 고침
- b) 조사 범위를 바꾼다
  메모로 적기
- c) 나중에
  패널·다른 일이 먼저

**권장 a) 이 방식으로 조사**
지금까지는 가설(포인터 꼴, 프롬프트 매칭)을 먼저 세우고 쟀다. 실제로 놓친 순간을 먼저 모으면 매핑이 안 되는 상황의 모양이 보인다.
