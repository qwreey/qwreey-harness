# Q38. 훅 백엔드를 Rust 로 옮길까? (벤더 중립, CPU·메모리, 유지보수)

## 맥락

사용자 원칙: 벤더 중립. mod 는 UI(desk)에만 쓰고 검사 백엔드로는 쓰지 않음. "어뎁터로는 mod가 맞을 수 있는데 그 백엔드는 좀.. 애초에 난 rust 잘 쓰던 사람이 맞기도 해서"

훅 한 번을 매번 새로 띄울 때 CPU(`.claude/audit/66-hook-server-language/one-shot.md`)
- Rust 바로 실행: 0.5~0.6 ms
- Rust `sh -c`: 1.2~1.5 ms
- python(지금): 34 ms

-> Rust 면 데몬 없이 도구 한 번(훅 약 17개)에 10~20 ms. 지금은 440 ms. 명령 훅만 있는 다른 하네스에서도 같은 바이너리가 돎.

모양(a 일 때)
- 저장소 하나에 Cargo 워크스페이스. 플러그인마다 바이너리 하나, 공통 코드는 컴파일 때 공유. `lib/` 바이트 사본과 sync-copies 가 필요 없어짐.
- 하네스마다 어댑터 설정만 다름. Claude Code 는 hooks.json 의 `command`+`args`(셸 없이).
- coderag 와는 잇지 않음(원칙). 같은 Rust 라 짜는 방식만 참고.

위험
- 플랫폼별 바이너리 배포: release + GPG 원칙대로. Windows 의 `.exe` 를 hooks.json 이 어떻게 가리킬지 확인 필요.
- 약 만 줄 다시 쓰기. 지금의 python 재생 시험을 바이너리에 붙여 결과가 같은지 대조.

## 선택지

- a) Rust 매번 실행, 플러그인별 바이너리, 뜨거운 훅부터
  데몬 운영 없이 60~70 배 줄고 벤더 중립·플러그인 독립 유지. 타입·도구로 읽고 검토하기 쉬움. 매 도구마다 뜨는 훅(sessions, advisor, proc-guard, conventions)부터 플러그인 단위로
- b) 계획만 먼저 쓰고 debate 로 확정
  오래가는 결정이라 배포(Windows, 서명), 옮기는 순서, 시험 대조 방법을 계획에 적고 두 편 토론을 거친 뒤 시작
- c) python 데몬
  로직은 그대로. 데몬 운영이 필요하고 다른 하네스에도 데몬을 올려야 하며, 읽기 어려운 코드는 남음
- d) 지금은 두고 matcher 좁히기만
  일이 가장 적음. 절반쯤만 줄고 유지보수 문제는 그대로

**권장 b) 계획만 먼저 쓰고 debate 로 확정**
방향은 a 가 맞아 보이지만, 만 줄을 옮기는 오래가는 결정이라 배포(Windows, 서명)와 옮기는 순서, 결과 대조 방법을 계획에 적고 토론으로 약한 곳을 찾은 뒤 시작하는 게 안전함. 그동안 실사용 주간은 지금 훅으로 돌고, 계획 단계에서 일이 버려지지 않음
