# Q38. 훅 CPU 를 어떻게 줄일까?

## 맥락

실측(2026-11-19, CPU user+sys, 이 세션의 62 MB 트랜스크립트로):
- 훅 하나 20~60 ms. 그중 python 켜기 약 11 ms, `json`+`re` 약 16 ms, 나머지 대부분 모듈 불러오기와 정규식 컴파일. 검사 로직은 거의 0.
- `-X utf8` 은 차이 없음.
- 도구 한 번에 드는 CPU
  - Bash: 17개, 약 0.44 초
  - Edit: 약 0.33 초
  - Read: 약 0.15 초
  - 사용자 말: 약 0.23 초
- 같은 단계의 훅이 동시에 떠서 도구마다 코어 하나가 잠깐 꽉 참.

사용자: "컨벤션 체커, 그런것들이 cpu를 너무 많이 소모하더라 ... 요청 받는 데몬으로 만들어야하나 싶은 느낌"

Claude Code 공식 훅 종류에 `type: "http"` 가 있음(이벤트 JSON 을 POST, 응답 JSON 은 명령 훅과 같은 형식, 연결 실패는 막지 않는 오류).

## 선택지

- a) 파이썬 다이어트 먼저, 그다음 http 데몬 시험
  다이어트(바로 끝내기, 모듈 나중에 부르기, matcher 좁히기)로 절반 안팎. 위험 낮음. 그 뒤 훅 하나를 http 로 옮겨 CPU 와 데몬이 죽었을 때를 재고 넓힐지 정함
- b) 다이어트만
  구조는 그대로. 절반쯤 줄고 끝
- c) http 데몬으로 바로
  띄우는 비용이 거의 0. 데몬 켜고 끄기, 포트·인증, 코드 다시 읽기를 만들어야 하고, 막는 훅은 데몬이 죽으면 통과되니 명령 훅으로 남김
- d) mod(TypeScript, Claude Code 안)로 옮기기
  데몬 없이 비용 0(desk 가 이 방식). 대신 훅 약 20개를 다시 써야 해서 가장 큼

**권장 a) 파이썬 다이어트 먼저, 그다음 http 데몬 시험**
비용 대부분이 프로세스와 불러오기라, 싼 다이어트로 절반을 먼저 줄이고, 큰 구조 변경(http 데몬)은 훅 하나로 재 보고 정하는 게 안전함. Rust 는 띄우는 비용이 남고 다시 쓰는 양이 커서 뺌
