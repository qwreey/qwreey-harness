## §1 결론 한 줄
메타테이블이 붙은 테이블 **자신의 정수 키 칸**(`t[i]` 읽기·쓰기)만 느려진다. 이 세금은 `-O1` 1.6 배에서 native 로 가면 **읽기 2.1 배, 쓰기 4.4 배**로 커진다. 상수 문자열 필드(`o.n`)와 메타테이블 없는 안쪽 표(`o.data[i]`)는 영향이 없다. 그러니 원소는 메타테이블 없는 표에 둔다.

## §2 정수 키 칸 세금 (모드별 재측정)
status: verified · last-confirmed: luau 0.742 (0.734 대조) · 근거: `bench/mt-index.luau`(read, write 그룹), 소스 Luau 0.742 `VM/src/lvmexecute.cpp:779,809,836,864`(audit/09 ★1), 후보 S-P01

원인(소스): `GETTABLE`/`SETTABLE`/`GETTABLEN`/`SETTABLEN` 의 배열부 빠른 경로는 `!h->metatable` 일 때만 탄다. 메타테이블이 있으면 `__index` 가 없어도 느린 경로(`luaV_gettable`)로 빠진다. 그래서 **메타테이블의 존재 자체**가 원인이다.

100만 원소, 같은 루프 함수에 표만 바꿔 넣음. 칸 = 메타테이블 없는 표 대비 배수, 프로세스 3개의 중앙값(범위).

| 접근 | 0.734 `-O1` | 0.742 `-O1` | 0.742 `-O2` | 0.742 `-O2 --codegen` |
|---|---|---|---|---|
| 읽기 `acc += t[i]`, 빈 MT | 1.58 (1.55–1.58) | 1.62 (1.60–1.64) | 1.70 (1.65–1.91) | **2.09** (2.00–2.18) |
| 읽기, `__index` MT | 1.57 | 1.63 | 1.67 | 2.08 |
| 읽기, `table.freeze` + MT | 1.60 | 1.60 | 1.74 | 2.08 |
| 쓰기 `t[i] = t[i] + 1`, 빈 MT | 1.74 (1.73–1.76) | 1.82 (1.79–1.84) | 1.83 (1.82–1.97) | **4.39** (4.26–4.44) |
| 대조군(같은 코드 반복) | 0.99~1.00 | 0.98~0.99 | 1.01~1.03 | 0.99~1.00 |

원천 수치와 비교:

| 원천 | 조건 | 원천 값 | 이번 값(같은 조건) | 판정 |
|---|---|---|---|---|
| stl perf 1절 | 0.734 `-O1`, 200만, 최소값 | 1.59x | 1.58x | 같음 |
| stl perf 18절 | `-O1` / `-O2` / `--codegen -O2`, 9회×3 | 1.60 / 1.66~1.81 / 1.96~2.00x | 1.62 / 1.70 / 2.09x (0.742) | 같음 |
| stl perf 16절 | `-O2`, MT 제거 시 쓰기 0.58x(= MT 1.72x) | 1.72x | 1.83x | 같음 |
| (새 측정) | native 쓰기 | 없음 | **4.39x** | 원천에 없던 값. native 에서는 쓰기 세금이 읽기의 두 배다 |

읽는 법: 메타테이블 없는 쪽만 빨라지기 때문에(`-O1` 4.5 ms → native 2.8 ms, 쓰기는 7.0 → 2.7 ms) 배수가 커진다. 메타테이블 쪽 절대 시간은 모드 사이에 거의 그대로다. 배포 조건(Roblox 라이브 `-O2`, 서버 native)일수록 이 세금이 결정적이다.

## §3 세금이 없는 접근
status: verified · last-confirmed: luau 0.742 (0.734 대조) · 근거: `bench/mt-index.luau`(field, inner 그룹), 후보 S-P02, audit/09 §6 모순 3(범위 차이로 판정)

| 접근 | 0.734 `-O1` | 0.742 `-O1` | 0.742 `-O2` | 0.742 `-O2 --codegen` |
|---|---|---|---|---|
| 상수 문자열 필드 `o.n` (MT 대 없음) | 1.00 | 1.00 | 1.02 | 1.03 |
| 안쪽 표 `local d = o.data; d[i]` (겉표에 MT) | 1.00 | 1.00 | 0.98 | 0.99 |

- 상수 문자열 키는 `GETTABLEKS` 의 인라인 캐시가 그 칸을 바로 읽는다. 키가 표에 **있으면** 메타테이블을 보지 않는다.
- stl perf 1절 "MT 가 있으면 인덱싱 1.59 배"와 60절 "칸·필드 읽기는 MT 무관"은 모순이 아니다. 앞은 겉표의 정수 칸, 뒤는 필드와 안쪽 표다.

## §4 피하려는 시도와 그 결과
status: verified · last-confirmed: luau 0.742 · 근거: `bench/mt-index.luau` read 그룹, `snippets/perf-table-move-raw.luau`, `snippets/perf-ipairs-raw.luau`, 후보 S-P01, S-P03, S-P32

| 시도 | 결과 (MT 없는 `t[i]` 대비, 0.734 `-O1` / 0.742 `-O1` / `-O2` / native) | 판정 |
|---|---|---|
| `rawget(t, i)` | 1.62 / 1.63 / 1.66 / 1.40 | 못 피한다. 함수 호출 값이 든다 |
| `table.freeze` | 위 §2 표와 같음 | 못 피한다 |
| `ipairs(t)`, `for _, v in t` 로 돌기 | MT 표 숫자 for 대비 0.46 / 0.45 / 0.45 / 0.41 | **피한다.** 둘은 raw 로 돈다(`iteration.md` §2) |
| `table.move` 로 복사 | MT 원본도 MT 없는 원본과 같은 값(`tables.md` §6) | **피한다.** C 에서 raw 로 복사한다 |
| 루프 밖에서 `local d = o.data` | §3 | **피한다.** 원소를 안쪽 표에 두는 구조일 때 |

주의: `ipairs`·일반화 for·`table.move` 는 **`__index` 를 보지 않는다**. 메타테이블로 없는 칸을 채워 주는 표에서는 결과가 달라진다(`perf-ipairs-raw.luau`, `perf-table-move-raw.luau`).

## §5 생성 비용과 메모리: 메타테이블 대 메서드 복사
status: verified · last-confirmed: luau 0.742 (0.734 대조) · 근거: `bench/mt-create.luau`, 후보 S-P05(X-21 병합)

5만 개 생성. 기준 = `{ n = 0, data = {} }` 맨 표.

| 생성 | 0.734 `-O1` | 0.742 `-O1` | 0.742 `-O2` | 0.742 native | 원천(0.734 `-O1`) |
|---|---|---|---|---|---|
| `+ setmetatable(…, Mt)` | 1.11 | 1.12 | 1.11 | 1.07 | +14~21 ns / 50 ns (60절) |
| 메서드 54개를 인스턴스에 복사 | 39.0 | 36.0 | 36.9 | 38.7 | 20.4 배(1-부절, 작은 배열 기준) |

| 객체당 메모리(작은 배열 2칸) | 모든 모드 | 원천 |
|---|---|---|
| 메타테이블 없음 | 80 B | — |
| 빈 메타테이블 붙임 | 80 B | 96 B |
| 메서드 54개 복사 | 2128 B | 2112 B |

- 메타테이블 참조는 표 머리에 있는 칸이라 객체 메모리를 늘리지 않는다. 원천의 96 B 는 모양이 다른 표였을 가능성이 높다(재현 안 됨, 결론에는 영향 없음).
- 복사 방식은 20 배가 아니라 **36~39 배** 느렸다(원천은 다른 모양의 배열을 썼다). 결론은 같다: **작은 객체를 많이 만들면 메타테이블 방식이다.**

## §6 구조 처방
status: verified(§2~§5 수치에서 유도) · 근거: 후보 S-P01, S-P02, S-P05, stl-luau-doctor/.claude/base/perf-measurements.md 16·16-2절

1. **원소가 많은 컨테이너는 원소를 메타테이블 없는 안쪽 표에 둔다.** `{ data = {...}, n = 0 }` + 메타테이블. 겉표에는 상수 문자열 필드만 둔다. stl 은 원소가 겉표에 직접 사는 `Arr` 에서만 MT 를 떼고 큰 이득을 봤다(`-O2` 쓰기 0.57x, 읽기 0.70x). `{data, size}` 래퍼인 맵·셋·힙은 0.98~1.01x 로 변화가 없었다.
2. **원소가 겉표에 살아야 하면** 메타테이블을 붙이지 않고 모듈 함수(`Arr.Len(a)`)로 다룬다. 호출 모양 비용은 `calls-and-closures.md` §1.
3. 뜨거운 루프에서는 안쪽 표를 **루프 밖에서 지역으로 받는다**(`iteration.md` §4, 1.56~1.69x).
4. 순회는 의미가 맞으면 `ipairs`/일반화 for 를 쓴다. MT 세금을 우회한다.

## §7 메타메소드 규약
status: described(아래 표시한 것 외) · 원천: stl-luau-doctor/.claude/base/architecture.md:294-304, container-design-notes.md:279-283, rbvm/.claude/review/2026-10-05-code-review.md:686,711 · 후보 S-135(D-R36 병합), R-26

- `__eq` 는 두 피연산자가 같은 종류(둘 다 표 또는 둘 다 userdata)이고 같은 메타메서드일 때만 불린다.
- `__index` 는 함수보다 **표**를 가리킬 때 싸다(함수 호출이 없다). described, 미측정.
- `__metatable` 로 잠긴 표를 `for … in` 으로 돌면 숨은 `__call`·`__iter` 를 따라간다.
- Luau 테이블에는 `__gc` 가 없다(Q-010). "사라지는 순간" 훅이 필요하면 명시적 해제 API 를 둔다.
- `table.freeze` 된 표라도 **없는 키**에 대입하면 readonly 검사보다 `__newindex` 가 먼저 불린다(R-26, luau CLI 실측 원천). frozen 프록시로 쓰기를 가로챌 수 있다는 근거다.
