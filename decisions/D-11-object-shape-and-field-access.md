## 2. 실제 근거

- **성능**(stl perf §14·§16·§18) [기록]
  - 같은 함수를 `a:Len()` 1.00x, `Arr.Len(a)` 0.82x, `local Len = Arr.Len; Len(a)` 0.64x 로 쟀다.
  - 메타테이블이 붙으면 `t[i]` 가 1.59배다(빈 메타테이블도, `rawget` 으로도 못 피함). `-O2`/codegen 에서는 1.66~2.00배다.
- **정확성**(quad H-174) [기록]
  - 백엔드가 나중에 주입하는 값을 Init 에서 지역으로 받으면 설치 전 스텁이 영원히 남는다.
  - devplorer 의 "재대입되는 상태"도 같은 원리다.
- **BI 전환의 근거**: 실사용 프로그램을 짜 보니 네임스페이스만으로는 불편했다. 세부는 `stl-luau/.claude/research/class-like/`. [기록, 진행 중]
- **타입**: tbox 는 "메서드의 `self` 를 `any` 로 선언한다(자기 참조 시그니처가 new solver 에서 불일치를 놓침)"고 적었다(`packages/tbox/CLAUDE.md:111`). stl 은 "자기 자신을 돌려줄 땐 `return self :: any`"(`conventions.md:42`)라고 적었다. 같은 솔버 한계를 각자 다르게 우회한다. [기록]
- 두 입장(1-2)은 **충돌하지 않는다.**
  - quad·devplorer 는 "바뀌는 값"을 다룬다.
  - stl 은 "바뀌지 않는 함수 + 뜨거운 루프"를 다룬다.
  - quad 의 "이득이 없다"는 발언은 뜨거운 루프가 아닌 초기화·이벤트 경로에 대한 것이다.

## 3. 합의안

### 안 A. 조건부 규칙(필드 읽기) + 객체 모양은 저장소 설계
- 필드 읽기 규칙은 셋이다.
  1. **나중에 주입·재대입되는 값**(백엔드 op, 서버 상태)은 매번 `Module.x` 로 읽는다. 지역 캡처와 위임 래퍼를 만들지 않는다.
  2. **바뀌지 않는 함수·테이블**은 실측된 뜨거운 루프에서만 지역으로 받는다. 그 밖에서는 굳이 받지 않는다.
  3. 성능 주장은 실측으로 한다.
- 객체 모양(메타테이블 메서드냐 네임스페이스냐)은 공통 규칙에 두지 않는다. 사실(1.59배 인덱싱 세금, 콜론 호출 비용)만 스킬에 둔다.

|---|---|
| 전부 | 0 |
| stl | `GEMINI.md` AB 서술 정정(이미 P0 위생 항목) |

### 안 B. 공통 기본값 "메서드 객체 + 같은 이름 네임스페이스 함수"(stl BI 형)
- 새 라이브러리의 기본 모양으로 권한다. quad·tbox 의 현재 모양과도 대체로 맞는다.
- 다만 stl 자신이 아직 전환 중이고 `research/class-like/` 가 정본이라, 확정 전에 공통화하면 되돌릴 위험이 있다.

## 4. 추천: 안 A

- 필드 읽기의 두 입장은 조건만 다르고 모순이 없다. 조건문 하나로 합의가 끝난다.
- 객체 모양은 저장소마다 설계 결정(AB/BI, Brand, Kind)의 핵심이다. 공통 규칙이 끼어들 자리가 아니다. 스킬에는 성능·타입 사실만 둔다.
- stl BI 가 확정되면 안 B 를 "새 저장소 기본값"으로 다시 검토한다.
