# Code reuse

## Values
- In code that runs against other repos or projects (tools, plugins, libraries), a value two projects could reasonably want different (folder or extension lists, size limits, stage ladders, tool names) is policy: read it from config, with a `DEFAULT_*` fallback in code. Values fixed by a format, spec, outside tool or correctness stay `const`.
- `DEFAULT_` promises an override; do not use the prefix for a value nothing overrides.
- A value two sides must agree on (client and server, two scripts of one game) lives in one shared module both require. A "same as X" comment is an unchecked copy.

## One definition
- Before writing a helper (parser, walker, hash, glob, date, string trim) or a list of names (statuses, kinds, levels), search for one this package can import, and use or extend it. Two copies of one fact drift apart.
- A copy this package cannot import (separately installed package, another repo, another language): keep it, mark it `@copy-of: <path>[#NAME]` in a line comment (or wrap copied lines in `@start-replace: <path>#<NAME>` ... `@end-replace`), and compare it with the source in a test, or generate one from the other. Where the repo has `tools/sync-copies.py`, edit the canon (`lib/`) and run it with `--apply` instead of editing copies. Do not replace it with an import across the package boundary. Vendored trees are not marked or edited: change the source and re-vendor.
- A literal checked against a type (a Luau or TS union) already references it. Names owned by an outside API (engine classes, tool names) are not your vocabulary.
- A list that mirrors a union: TS derives the union from the list (`(typeof LIST)[number]`); Luau annotates the list with the union type.

## Libraries
- Hand-writing a parser or algorithm that a well-known library provides: put `why not <library>: <reason>` at the top of the module (measured size or startup budget, exact parity with a reference, tolerant parsing, the runtime cannot install it). Adding a dependency is the user's call; propose it with measured cost (size, build time, dependency count).

## Scope
- Apply this to code you add. Do not refactor existing code for it unprompted; old duplicates in edited files are reported to the user at turn end.
- Before you add a `@copy-of` or `@start-replace` marker, or act on a reuse notice, load the `qwreey-conventions:code-reuse` skill. A repo's own rules win.
</rule>

# Code structure (file length, folders, data) - all toolkits

> If the repo's `.claude/rules/`, `conventions.md`, or `.claude/structure.json` says otherwise, follow the repo.
> Pairs with the PostToolUse hook `structure-reminder`. The hook only informs; it never blocks.

## File length
- Check the target file's line count before adding a feature. Tests get double the limits; generated and pure-data files are excluded.
  - Over 800 lines: name the group to split out, in one line of your work report.
  - Over 1,500 lines: ask the user for a split plan before appending anything.

## Exemptions
- A file may stay over the limit for a solid reason, e.g. type limits, generated code, pure data.
- Record the reason in one of two ways:
  - `<comment> @structure-exempt: <reason>` within the first 10 lines of the file (`--`, `//`, `#`).
  - an entry in `exempt` in `structure.json`.
- No reasonless exemptions ("later", "too much work").

## How to split
- Do a move-only commit first; fix things in the next commit.
- After moving, fix stale paths left in docs and check the seams.
- Do not re-attach features to the leftover chunk. Extract shared state first into a state table or module.

## Folders
- Three or more files with the same prefix in one folder: group them into a `prefix/` folder.
- More than 15 sources of different kinds in one folder: propose a grouping.
- The repo decides the top-level categories (layer, kind).

## Data
- Per-item data with a uniform shape (request name, args, cost, permission, batch, ...) goes in one table; code reads the table.
- If one variable is branched on by string in more than 8 ways, consider replacing the branches with a table.
- Tool-generated data goes in its own file, with the generator path and "do not edit by hand" in the header.

## Naming
- If a user-chosen name or structure conflicts with these rules, do not rename right away. Propose the change with reasons; do bulk edits only after approval.

## Toolkit details
- Luau: `luau-style` skill: `references/structure.md` (cases), `references/splitting.md` (split strategy), `scripts/split-plan.py` (split planner).
- Other toolkits: none yet. Fill in after the toolkit is imported (`/q:doctor` `references/toolkits/`).
</rule>
<rule plugin="qwreey-conventions" name="comments">
# Comments
- Write why: the constraint, the trap, the reason for an odd-looking choice.
- History (dates, ledger ids, rounds, who decided) goes to the commit message, CHANGELOG or ledger. Existing ids are never deleted; move them to a `Ref:` tail line.
- Type only what a keyboard types: ASCII and the file's comment language. A symbol a person did not type marks the comment as machine-written, and editors draw spaces as a faint middle dot, so symbols are easy to misread. Common slips: em dash or en dash (write ` - ` or `:`), middle dot (comma or `/`), ellipsis character (`...`), arrows (`->`), `§` (omit), circled digits (`1)`), curly quotes, emoji (`ok`, `FAIL`, `NOTE:`). Never write a character as a `\uXXXX` escape in a comment.
- Fix only comments you touch anyway; old problems in edited files are reported to the user by the hook at turn end, not cleaned up unprompted.
- Korean comments keep the file's sentence ending (합니다체 or 한다체).
- No banners, capitals or IMPORTANT for routine notes; skip ceremony words.
- On a notice, fix the named lines; leave a deliberate exception and say so once in your report.
- A repo's own rules win.
</rule>
