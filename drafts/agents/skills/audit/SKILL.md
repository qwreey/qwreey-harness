# /audit — 관점별 감사 → 교차 검증 → 원장

인자: `$ARGUMENTS`

- **관점들**: `types`, `runtime`, `quality`, `perf`, `docs`를 쉼표로 잇는다. 생략하거나 `auto`이면 0단계 표로 고른다.
- **대상**
  - `diff`(기본): 작업 트리 변경과 미추적 파일
  - `<경로…>`: 지정한 파일·디렉터리
  - `<rev범위>`: 예) `HEAD~5..HEAD`
- `--rounds N`: 최대 라운드 수. 기본 3.
- `--serial`: 관점을 한 번에 하나씩 띄운다. 토큰이 빠듯하거나 프로젝트가 직렬을 요구할 때 쓴다.
- `--deep`: 이번 호출만 감사자를 `model: "opus"`로 띄운다(Agent 호출의 model 인자).

이 절차의 원칙은 넷이다.
1. 감사자는 읽기 전용이고 보고만 한다.
2. 판정과 수정은 메인이 한다.
3. 애매한 것은 사용자에게 묻는다.
4. 감사는 다음 작업을 막지 않는 유한 절차다.

## 0. 준비 (메인)

1. **프로젝트 규약을 먼저 확인한다.** 프로젝트 `CLAUDE.md`나 conventions에 감사 규약이 있으면 그것이 이 스킬보다 우선한다. 예: "감사자는 한 턴에 하나", 원장 위치, 번호 체계.
2. **대상을 확정한다.** 기준 커밋, 바뀐 파일 목록, 이번에 뒤집히거나 새로 확정된 결정을 한 문단으로 정리한다. 감사자 프롬프트에 그대로 들어간다. 범위의 기본은 diff와 그것을 인용·참조하는 곳까지다. 전 코퍼스 스윕은 오래 안 돌렸을 때만 한다.
3. **관점을 고른다(auto)**

   | 바뀐 것 | 관점 |
   |---|---|
   | `*.luau`의 공개 타입, 제네릭, 타입 테스트 | types |
   | 정리 경로, 연결, 캐시, 스케줄링, mock·엔진 경계 | runtime |
   | 새 모듈, 새 공개 이름, 큰 리팩터 | quality |
   | 문서, `.claude/` 설계 문서, CLAUDE.md | docs |
   | 핫 경로 또는 성능 수치 | perf (자동 선택하지 않는다. 사용자가 지정하거나 메인이 제안만 한다) |

   - `*.luau`가 바뀌었으면 기본은 types와 runtime이다. quality는 새 모듈이나 공개 이름이 있을 때만 더한다.
4. **비용을 알린다.** 띄울 감사자 수와 모델을 사용자에게 한 줄로 알린다. 셋 이상이거나 `--deep`이면 확인을 받는다. 참고로 sonnet 감사 한 패스가 수만~20만 토큰까지 썼다.
5. **가드 스냅샷을 찍는다.** 감사자가 트리를 바꾸지 않았는지 나중에 비교한다. 같은 컨테이너에서 여러 세션이 돌기 때문에 경로에 저장소 이름과 시각을 넣는다. 출력된 경로를 기억해 둔다.
   ```bash
   G=/tmp/claude-audit/guard-$(basename "$(git rev-parse --show-toplevel)")-$(date +%Y%m%d-%H%M%S)
   mkdir -p "$G" && git rev-parse HEAD > "$G/head" && git status --porcelain=v1 | sha1sum > "$G/status" && echo "$G"
   ```
6. **원장 위치를 정한다.**
   - 프로젝트가 리뷰 원장을 두면(CLAUDE.md 온디맨드 표, `.claude/review/`, `.claude/qa-request/` 등) 그 파일과 번호 체계를 쓴다.
   - 없으면 `.claude/review/audit-<YYYY-MM-DD>-<slug>.md`를 새로 만든다. 발견 번호는 `A-001`부터, 문항 번호는 `Q-001`부터 쓴다.

## 1. 감사자 띄우기

관점마다 `Agent(subagent_type=<luau-…-auditor|docs-auditor>)`를 쓴다. 기본은 **한 메시지에 병렬**(최대 3)이다. `--serial`이거나 프로젝트 규약이 직렬이면 하나씩 띄운다.

**한 관점을 파일 조각으로 쪼개 여러 감사자에게 나누지 않는다.** 조각 맥락은 결정 이력을 몰라 새 메커니즘을 발명하거나, 이미 추적된 것을 서로 다시 찾는다. 병렬은 관점 사이에서만 한다. 관점끼리는 증거를 얻는 방식(음성 대조군, 프로브, 대조)이 달라서 맥락을 나눠도 된다. docs는 문서 추론이라 늘 단일 맥락이다.

프롬프트 틀(관점마다 같은 틀에 범위만 바꾼다):

```
관점: <types|runtime|quality|perf|docs>
기준 커밋: <hash> (직접 `git rev-parse HEAD`로 확인할 것)
범위: <바뀐 파일 목록 또는 경로> — 그 코드를 인용·참조하는 곳까지 넓혀 본다.
이번에 바뀐 결정: <한 문단, 없으면 "없음">
이번 라운드 각도: <예: 1라운드 = 바뀐 파일 자체, 2라운드 = 그것을 쓰는 쪽, 3라운드 = 테스트·문서>
기보고(다시 올리지 말 것): <원장 경로>, <archive/ 경로>, <알려진 한계 문서>
마지막 메시지 하나에 최종 목록 전부. 다 못 본 것은 '미완'으로 표시.
```

## 2. 수거와 가드

- `task-notification`의 `status: completed`가 곧 종료다. 본문이 "나중에 보내겠다"고 해도 기다리지 않는다. 미완 항목은 메인이 판정하거나 다음 라운드로 넘긴다.
- 가드를 비교한다.
  ```bash
  G=<0단계에서 출력된 경로>
  [ "$(git rev-parse HEAD)" = "$(cat "$G/head")" ] && \
  [ "$(git status --porcelain=v1 | sha1sum)" = "$(cat "$G/status")" ] && echo unchanged || echo CHANGED
  ```
  - 바뀌었으면 누가 바꿨는지 확인한다(메인, 사용자, 감사자). 감사자가 바꿨으면 그 감사자의 보고를 신뢰하지 않고, 바꾼 내용을 사용자에게 보인 뒤 되돌릴지 묻는다.

## 3. 교차 검증 (메인)

발견마다 다음 순서로 판정한다.

1. **중복 묶기**: 관점이 달라도 같은 `파일:줄`이나 같은 메커니즘이면 하나로 묶는다. 묶은 발견에는 관점을 모두 적는다. 여러 관점이 독립적으로 같은 것을 찾았으면 확신도를 올린다.
2. **충돌 찾기**: 예를 들어 types는 "건전", runtime은 "크래시"라고 할 수 있다. 이런 충돌은 메인이 직접 재현해서 가른다.
3. **기보고와 기각 이력 확인**: 원장, `archive/`, "검토 후 안 만들기로 한 것" 목록을 grep한다. 이미 있으면 번호만 잇는다.
4. **재현**
   - `높음`은 메인이 반드시 직접 재현하거나 대조한다.
   - `중간` 이하는 감사자의 재현 스니펫을 한 번 돌려 본다.
   - 재현이 안 되면 "감사자 주장, 메인 미재현"으로 남기고 고치지 않는다.
5. **세 갈래 판정**
   - ① 정본이 이미 답을 가진 결함이면 원장 번호를 붙이고 메인이 고친다.
   - ② 새 필드·인자·이름·메커니즘이 필요하거나 정본과 충돌하면 사용자 문항으로 올린다. 증상만 확실하면 "증상 확정, 처방 미정"으로 둔다.
   - ③ 대조해 보니 건전하면 확인 기록으로 남긴다.
6. **사용자 인용문 옆에 감사자 제안을 붙이지 않는다.** 감사자의 말은 사용자의 말이 아니다. 원장에서는 "감사자 주장", "메인 확인", "사용자 결정"을 칸으로 가른다.

## 4. 원장 기록

원장이 없으면 다음 모양으로 만든다(평문, 기호 나열로 압축하지 않는다).

```markdown
# 감사 <YYYY-MM-DD> <slug>

기준 커밋 `<hash>`, 범위 <…>, 관점 <…>, 감사자 모델 <…>, 라운드 <n>.
감사자 원 보고서: <경로 — 보존할 가치가 있으면 `.claude/review/raw/<날짜>-<관점>.md`>

| 번호 | 관점 | 무엇 (평문 한 문장) | 위치 | 확인 | 처리 |
|---|---|---|---|---|---|
| A-001 | runtime | … | `src/x.luau:120` | 메인 재현 | 고침 `<커밋>` |
| A-002 | types | … | `src/y.luau:40` | 감사자 주장, 메인 미재현 | 보류 |
| A-003 | quality | … | … | 메인 대조 | 문항 Q-001 |

## 문항
- **Q-001** 상황 → 무엇이 막히나 → 갈래마다의 뜻 → 메인 권고. 평문 한 문단.

## 건전성 확인
- …
```

- **확인** 칸에는 다음 중 하나만 쓴다: `메인 재현`, `메인 대조`, `감사자 주장, 메인 미재현`, `여러 관점 독립 발견`
- **처리** 칸에는 다음 중 하나만 쓴다: `고침 <커밋>`, `문항 Q-nnn`, `확인 기록`, `보류(이유)`

## 5. 라운드와 종료

- 메인이 고친 뒤 다음 라운드를 띄운다. 라운드마다 **각도를 바꾼다**. 예: 바뀐 파일 → 그것을 쓰는 쪽 → 테스트와 문서. 고친 부분 자체가 새 결함을 만드는 일이 반복 관측됐으므로, 고친 범위는 다음 라운드 범위에 넣는다.
- **새 발견이 0인 라운드가 나오거나 `--rounds`에 닿으면 끝낸다.** 수렴하지 않고 멈추면 조용히 끝내지 않는다. "몇 라운드에서, 라운드별 발견 수 몇, 왜 멈췄는지"를 보고한다. 수렴하지 않은 감사를 "통과"로 쓰지 않는다.
- 같은 diff에 리뷰를 여러 번 돌리지 않는다. 반영분의 재검증은 다음 라운드 감사자의 몫이다.
- `/code-review`는 이 감사를 대체하지 않고, 이 감사도 `/code-review`를 대체하지 않는다. 감사자는 관점별 의미를 보고, code-review는 diff 안의 국소 결함을 본다. 큰 변경에는 둘 다 권한다.

## 6. 사용자에게 보고

다음 순서로 짧게 쓴다.
1. 라운드별 발견 수
2. 고친 것(커밋)
3. 사용자 문항(평문, 메인 권고 포함)
4. 메인이 재현하지 못한 감사자 주장
5. 안 본 범위

감사자의 주장과 메인의 검증 결과를 섞지 않는다.
