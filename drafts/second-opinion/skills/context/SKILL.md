# second-opinion:context — 대화를 이어받은 눈으로, 전환점마다

근거는 `audit/18` §11 이다(advisor 호출 시점 재현, opus·sonnet). 요지:
- 대화를 받은 쪽(이 스킬)은 advisor 가 잡은 "흐름에만 있던" 문제를 다시 잡았다. diff 를 받은 쪽(`second-opinion:audit`)은 0건이었다.
- 대신 diff 쪽은 실측 버그를 잡았고 이 스킬 쪽은 거의 못 잡았다. **둘은 대체재가 아니다.**
- fork(메인과 같은 프레임)는 다른 프레임보다 메인이 방금 만든 설계를 덜 의심했다(방향만, 표본 1). 그래서 기본은 fork 로 싸게 자주 쓰되, 무거운 전환점에는 다른 프레임을 쓴다.

## 1. 언제

| 시점 | 경로 | 이유 |
|---|---|---|
| 작업 단위를 끝내고 다음으로 넘어가기 직전 | fork | 싸다. 놓친 약속·미결 질문·병행 작업 영향 |
| 사용자에게 결정 확정·방향 전환을 제안하기 직전 | fork | 사용자 원문과 지금 제안이 어긋나는지 |
| apply·배포·설치 안내 직전, 되돌리기 어려운 확정 직전 | **other-frame** (+ 필요하면 `audit`) | 메인과 같은 사각지대를 피한다 |
| fork 결과가 "문제 없음"에 가깝고 일이 무겁다 | other-frame | 같은 프레임의 동의는 증거가 약하다 |
| 커밋 전 diff 정확성, 반복 실패, 구현 검증 | 이 스킬 아님 → `second-opinion:audit` | |

- 한 전환점에 한 번. 같은 질문을 fork 로 여러 번 돌리지 않는다(표본을 늘려도 같은 프레임이다).
- 저장소 등급(`HARNESS_REVIEW_TIERS`)이 `low`·`off` 이면 fork 만, `high` 면 apply 직전 other-frame 을 기본으로 한다.

## 2. fork 경로 (기본)

```
Agent(subagent_type="fork", description="second opinion: context", prompt=<아래 질문 블록>)
```

질문 블록 (그대로 쓰고 `<…>` 만 채운다):
```
[second opinion: context] 너는 이 대화를 이어받은 fork 지만, 지금부터는 메인이 아니라 검토자다. 작업을 이어서 하지 말고
파일을 고치지 말고 다른 에이전트에게 메시지를 보내지 않는다. 읽기 도구는 꼭 필요한 확인에만 쓴다.

메인은 이제 <다음 단계 한 줄> 로 넘어가려 한다.
질문: 이 흐름에서 놓친 것, 잘못된 전제, 확인 안 한 가정은?

메인이 방금 만든 설계와 결론을 '내가 한 일'로 변호하지 말고 남이 한 일처럼 의심한다. 특히:
- 방금 끝낸 설계가 다른 실행 경로(서브에이전트, auto-compact, 다른 저장소, ~/.claude 가 없는 환경)에서도 성립하나
- 병행 작업에 미치는 영향, 그쪽에 전달하지 않은 규약
- 사용자에게 묻고 답을 못 받은 질문, 아직 지키지 않은 약속
- 서브에이전트 보고의 "확인 못 함"이 사용자 보고에서 빠졌나
출력: 항목마다 무엇을 / 근거(대화 위치·파일:줄) / 왜 지금 중요한가 / 반드시·권장·참고. 확인과 추정을 나눈다.
마지막에 다음 단계 전에 할 일 3줄. 없으면 "발견 없음"과 본 범위.
```
- "검토자로 역할 바꾸기"와 "특히" 목록은 §11 에서 fork 가 놓친 쪽을 보강하려고 넣었다. **이 문구의 효과는 아직 재지 않았다**(§11.7).
- fork 는 메인과 같은 모델로만 돈다(모델 지정이 무시된다). 메인이 opus 면 opus 다.

**비용** [실측 + 추정, §11.5]
- fork 의 첫 호출은 메인이 방금 보낸 요청의 접두를 캐시에서 읽는다. 실측: 139,375 토큰 읽기, 새로 쓴 것 109 토큰.
- 30만 토큰 맥락, opus 5.5(캐시 읽기 $0.20/M) 기준: 읽기 약 $0.06 + 출력 약 $0.12 = 1회 약 $0.2. 도구를 두세 번 쓰면 약 $0.35.
- 메인이 한동안 쉬어 캐시가 식었으면(메인 1h, 서브에이전트 5m TTL) 전체를 다시 쓴다. 30만 토큰이면 opus 약 $1.5~2.4 다. 메인이 방금 응답한 직후에 부른다.
- 결과 보고는 메인 맥락에 들어가 이후 매 턴 읽힌다. 보고는 짧게 받는다.

## 3. other-frame 경로 (무거운 전환점)

메인 대화를 텍스트로 옮겨 **다른 시스템 프롬프트**(`agents/second-opinion-context.md`) 아래에서 읽게 한다. advisor 와 같은 조건이다.
```bash
python3 -I <이 스킬>/scripts/ask-other-frame.py --model <sonnet|opus> --note "<다음 단계 한 줄>"   # 백그라운드 권장
```
- 대화 사본은 `scripts/render-transcript.py` 가 만든다. 마지막 compact 경계부터(메인이 지금 보는 범위), 도구 결과는 앞 300자만. §11 에서 317k → 132k 토큰.
- Agent 도구로 넘기지 않는다. 사본을 프롬프트에 옮겨 적으면 그만큼 메인의 출력 토큰이 된다.
- 비용 [실측]: 첫 호출이 캐시 쓰기라 맥락 크기에 비례한다. 132k 토큰에서 opus $1.25(1h 쓰기), sonnet $0.49(5m 쓰기). 그래서 기본 TTL 을 5m 로 둔다. 같은 사본을 1시간 안에 다시 물으면 opus $0.33.
- 모델: §11 에서 opus 는 2회 모두 "병행 작업 주입 경로" 를 잡았고, sonnet 은 못 잡은 대신 다른 범위 밖 위험을 찾았다. high 등급은 opus.

## 4. 결과 다루기

`second-opinion:audit` §4 와 같다. 요약하지 않고 그대로 사용자에게 보이고, 받아들임/버림/확인 필요를 근거와 함께 적고, 원장에 남긴다(`--kind context --reviewer fork|ctx-opus|ctx-sonnet`).
- fork 의 보고는 1인칭("저는 …")으로 올 수 있다. 메인이 쓴 글처럼 보이지 않게 "context 검토(fork)" 라고 머리를 붙여 전한다.
- 재현 환경 탓일 수 있는 지적(진행 중인 작업을 "실패"로 본다 등)은 사실을 확인한 뒤 버린다.
