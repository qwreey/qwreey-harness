## Delegation (qwreey-operator)
- Implementation spanning 3+ code files, ~150+ new lines, or much reading of other code or docs goes to background subagents (fresh agents, not forks), so the user can keep talking with you. This works once the design is settled and written down (a file, or a structured brief). A probe that decides whether a design can work at all stays in main, with the user, because its assumptions are what is being tested. Also keep in main: small edits, a decision just made, docs and config, work that needs the user's answers midway.
- Split the work along independent seams (backend and frontend, separate modules) into one subagent each and run them in parallel: time drops, and no agent carries another part's context. Chain them only where one part needs another's result. Within one part, prefer one agent in small steps over new agents: review each result, bring it the user's decisions or concrete counter-evidence, and resume it with SendMessage, so it keeps what it has read (its cache lasts about an hour) and corrects its own mistakes. Each resumed turn rereads its whole context, so once that has grown large (the completion notice shows its tokens; past about 200k) or the next step needs little of what it read, give the next step to a fresh agent with a short brief instead. Follow a cap on concurrent agents if the user set or mentioned one. Tell the user in one line: what, how many, which models, expected size.
- Subagent models: haiku for read-only lookup only; anything that writes, runs, judges, reviews or measures gets sonnet or above, sized to the task. Implementers: opus by default; sonnet only for light, fully specified work where a mistake is cheap and easy to spot, never for security-related or theory-heavy code.
- Beyond the usual brief: quote the user's own words, give done criteria with the test command, and ask for a report of changed files, test output and open questions (so it does not settle ambiguities silently). If main or another subagent may touch the same files meanwhile, launch it with `isolation: "worktree"`: it commits on its worktree branch and main merges that branch and removes the worktree. Otherwise it must not commit.
- Check without redoing: rerun its tests and compare the report with the done criteria; open a file only where the report is vague or the tests do not reach. A large or risky diff goes to a fresh reviewer subagent; reproduce each finding before acting on it. Main commits.
